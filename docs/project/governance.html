Make authority visible.

Goose ARWP is an open-source project with a maintainer-led product direction. Governance explains who can decide, how evidence changes the system, and where commercial relationships must be kept separate from technical truth.

Maintainer

Dzmitryi Kharlanau is the current named maintainer and owner identity in the project graph. The maintainer controls roadmap priorities, public product naming and merge decisions unless that model is explicitly changed later.

Contributors

Contributions can improve code, evidence, documentation, datasets and experiments. Contribution acceptance does not transfer general project governance or create an employment, agency or partnership relationship.

Upstream authorities

Search providers, standards bodies and protocol owners remain authoritative only for their own documented systems. Goose records those sources; it does not become an upstream standards authority by citing them.

Company collaboration

Commercial and broader company collaboration is routed through Metalhead Cats. Commercial involvement does not override source evidence, experimental controls or the requirement to disclose a material relationship.

How a recommendation changes

  1. Observe an upstream change, real site problem or measured outcome.
  2. Record the source, date, applicability and uncertainty.
  3. Create or revise a hypothesis or recommendation without presenting association as causality.
  4. Implement on a bounded target with a verifiable production gate where applicable.
  5. Measure search, citation, recommendation, visit and useful action separately.
  6. Preserve neutral and negative outcomes.
  7. Challenge, revise or retire recommendations when newer evidence contradicts them.

Commercial conflict boundary

  • A paid, sponsored or reciprocal relationship must not be presented as independent adoption or independent validation.
  • Commercial support can fund work, but it cannot silently change an evidence label.
  • Partner or customer logos are not outcome evidence.
  • Comparison and recommendation content should disclose a material relationship where it can affect interpretation.
  • A collaborator may disagree with Goose conclusions; disagreement is not removed merely to preserve a partnership.

Release and compatibility posture

The project is currently pre-stable. Technical interfaces, schemas and modules can evolve. Stable identifiers, dated evidence and compatibility notes should be preserved when changes would otherwise make prior results impossible to interpret.

No fake enterprise promises. Goose should publish an SLA, support matrix, deprecation guarantee or formal steering committee only when the project actually operates one and can honor it.

Corrections, security and disputes

Material factual corrections use the public corrections ledger. Security reports use the repository security policy. Naming and rights questions use the corresponding project policy pages. Technical disagreements should be resolved through inspectable evidence and reproducible tests where possible.
