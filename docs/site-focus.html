SITE FOCUS / HOUSE PLAYBOOK

Own a problem.
Draw the boundary.

A site becomes harder to understand when every adjacent topic gets promoted into a first-class section. Define the problem territory first. Then let content, navigation, design and Search/AI work serve that territory.

THE SITE THESIS

One sentence before one hundred pages.

For [primary audience] who need to [solve a concrete problem], this site provides [distinct useful mechanism / evidence / tool] so they can [useful outcome].

Boundary rule: a related idea is not automatically an in-scope page. It must strengthen the site's primary problem, useful outcome or proof.

SCOPE LEDGER

Use three buckets.

IN

Directly solves the primary problem, explains the mechanism, supplies evidence or enables the next useful action.

ADJACENT

Supports the core problem but stays subordinate. It can live below a hub without becoming another identity for the site.

OUT

Interesting and related, but not important enough to the core problem. Defer it, remove it or give a genuinely distinct problem territory its own resource.

CITE GOOSE HOUSE HEURISTIC

Small architecture first.

1primary problem territory
≤3homepage problem lanes
≤5primary navigation destinations
1dominant action per page

These are house heuristics, not ranking factors or platform requirements. Their purpose is to force a coherent first draft. Change them when the site's real audience and evidence justify another architecture.

PAGE CONTRACT

Every route needs a job.

page_job: what this page helps the visitor do primary_question: the question it answers in_scope: what belongs here out_of_scope: what belongs elsewhere proof: source, data, example, tool or first-hand evidence primary_action: next useful step parent_hub: one canonical owning section

If a proposed route cannot fill this contract without duplicating another page, it is a backlog idea rather than a new URL.

HOMEPAGE

Make it a decision surface, not a sitemap dump.

Problem + boundary

State the problem, promise and anti-scope early enough that a first-time visitor knows whether this resource is for them.

Three routes

Organize first-order choices around user problems or outcomes. Internal technologies should usually remain one level deeper.

Proof + action

Show why the promise is credible, then make one next useful step visually dominant. Deep reference material stays available without competing with it.

VISUAL + PERFORMANCE

Be memorable without becoming heavy.

Recognizable

Use a small tokenized palette, strong type hierarchy and a few large compositional moves instead of generic component-grid styling.

Useful

Visuals should explain hierarchy, evidence or mechanism. Do not hide essential text in imagery or let decoration weaken contrast and keyboard access.

Fast

Prefer static HTML/CSS, self-hosted fonts, compressed modern media with explicit dimensions and no third-party JavaScript required for core content.

Use field Core Web Vitals where available and lab tooling as diagnostics. Do not convert a lab score or an arbitrary kilobyte target into outcome evidence.

AGENT LOOP GATE

Run focus before expansion.

When a site is new, being redesigned or has become broad, start with the arwp-site-focus skill. Record the site thesis, scope/anti-scope, problem lanes, primary navigation and page contract. Only then route the work into discoverability, content, technical eligibility, evidence or measurement specialists.
