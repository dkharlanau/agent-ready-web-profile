Maturity needs evidence.

A recognizable owner, clear rights and naming boundaries, usable collaboration routes, governance, useful data and a history of verifiable changes are more valuable than a collection of badges. Goose ARWP remains pre-stable. The inventory makes declarations inspectable without pretending they are independent certification.

Project & policy surfaces

The Project & Policies hub exposes copyright/reuse, names and marks, partnership/collaboration, governance and privacy. Existing security, corrections and history complete the current Goose maturity surface set. The machine-readable Project Surfaces manifest records semantic roles and applicability boundaries.

These are page jobs, not a page-count target. A different site can consolidate roles when that produces a clearer substantive page. Terms, SLA/status and other policy surfaces are conditional on actual product behavior.

What can be inspected now

Canonical entities connect Dzmitryi Kharlanau, the software, the website and research assets. The data catalog points to two real datasets, not newly invented research. Names & marks separate project-reserved naming roles from trademark registration. The measurement plan defines discovery, resource intent and independent adoption without inventing baseline numbers.

Security reporting, corrections, product history and configured build-provenance work remain in the Trust Center. The machine-readable evidence inventory links to their actual files.

What the checker verifies

Required project maturity roles when declared; local policy files and canonical/meta basics; unique entity identifiers; named ownership; graph-to-dataset-page identity, licensing and download declarations; explicit DOI states; and measurement definitions that distinguish unknown from zero.

node scripts/project-surfaces-test.mjs --site
node bin/arwp-maturity.mjs check docs/maturity/profile.json
node bin/arwp-maturity.mjs receipt docs/maturity/profile.json

The receipt hashes the observed files and profile. It is unsigned, local and not proof of historical publication, legal compliance, trademark clearance, security or search performance.

What still needs external evidence

No issued DOI or trademark clearance is claimed. Existing analytics source is not a verified provider account or complete privacy-compliance test. Proposed custom events are not yet instrumented. Attestations must be checked against a real released artifact. Independent usage and search impact need observations, not metadata.

A valid inventory does not establish that the project is mature. It establishes that the selected static declarations are consistent.

Apply the pattern without adding clutter

Start with the site's actual owner and useful pages. Reuse existing canonical identifiers. Cover project identity, rights, names/marks, collaboration, governance, contact routing, security, corrections and change history with as few substantive pages as clarity allows. Add privacy, terms, SLA/status or accessibility statements only when actual site behavior or commitments make them applicable.

The next evidence worth producing

Prioritize a reproducible dataset release with a data dictionary and checksums; a case study with a denominator, dates and negative results; an independently maintained implementation; and a release compatibility/support policy the maintainer can actually honor. These are separate work items, not completed achievements.

For suitable ML data, consider Croissant after validating real record extraction. For archival citation, publish an actual versioned archive record before adding its DOI. Do not mint datasets, organizations, awards or review counts merely to fill a schema.

Search boundary

Google documents normal SEO foundations for its AI features, not a requirement for an ARWP maturity file or policy-page set. Project policy surfaces serve clarity, reuse, collaboration and accountability. Their existence does not demonstrate ranking or recommendation gains.
