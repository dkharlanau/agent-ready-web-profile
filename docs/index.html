START WITH A CLEAR PURPOSE

Choose what matters.
Leave the rest out.

If every topic gets equal attention, visitors have to work out what your site is actually for. Pick the main problem you help with. Keep related topics in support of it, rather than turning each into another section.

GOOSE / WE DO

Help people find and use the best parts of your site.

  • Find problems that matter for this particular website.
  • Make important pages accessible, clear and genuinely useful.
  • Explain why a change is worth trying and how to check it.
  • See whether people found the page and whether it helped them do something.
GOOSE / WE DO NOT

Fill the site with articles just to look busy.

  • No guaranteed rankings, citations or recommendation claims.
  • No generic publishing volume as a substitute for a site thesis.
  • No special AI file presented as a shortcut to getting found.
  • No mystery score without showing the underlying problems.

PICK THE PROBLEM YOU HAVE

What's getting in the way?

Start with what you are trying to fix. The technical tools are still here when you need them.

01 / BE FOUND

Can people find your pages?

Check whether your important pages can be reached, opened and found through the site. Fix real obstacles before adding more content.

Find an applicable pattern → 02 / BE USED

Does the page actually help?

Give visitors a useful answer, example, comparison or tool. Cut anything that makes the answer harder to find.

Improve the useful surface → 03 / BE PROVEN

Did anything improve?

First check that your fix is live. Then look for changes in visits or useful actions. If nothing changed, that's worth knowing too.

Run the Growth Loop →

A starting point, not a search ranking rule: one core problem, up to three first-order lanes, up to five primary navigation destinations and one clear next step on each page. Change the architecture when the site's real audience gives you a better reason.

A SIMPLE WAY TO BEGIN

Make one change worth making.

Choose one issue you understand. Make a change you can check. Then decide whether to keep going.

01 / SCOPE

Know who you're helping.

Write down who comes to this page, what they need and what they should be able to do next. That is enough to start.

02 / CHANGE

Choose a fix with a reason.

Pick one or two suggestions that fit your site. Read why they matter, make the change and check the result.

Explore the pattern library
03 / LEARN

Look for a useful result.

A change being live is not the same as it helping. Look for relevant visits, better answers and completed tasks; keep the disappointing results too.

Start an improvement loop

HOW WE CHECK OUR ADVICE

Know what we know — and what we don't.

For every suggestion, you should be able to see why we suggest it, how to check the fix and what would show it actually helped. Passing a technical check does not mean more traffic.

SOURCE

Why try it?

Published guidance, a reviewable example or a clearly marked idea to test.

CHECK

Did we build it?

Check the live page, important links and the part you actually changed.

RESULT

Did it help anyone?

Look at meaningful visits, references or completed actions where data is available.

LIMIT

What is not proven?

We say when we have not measured something, or when a change had no clear effect.

Technical depth / ResolverAgents, APIs, standards

THE INTEROPERABILITY FOUNDATION

Help agents find their way around.

Without a resolver

  1. Search or scrape the site
  2. Guess which discovery file matters
  3. Read incompatible metadata shapes
  4. Silently choose when declarations disagree
  5. Lose why an interface was trusted
Integration depends on site-specific logic.
→

With ARWP Resolver

  1. Observe bounded public discovery
  2. Normalize existing standards and conventions
  3. Keep source authority with every interface
  4. Surface conflicts instead of hiding them
  5. Plan the best interface for the intent
Integration starts from inspectable evidence.
Website resolverCLI ready

Resolve all discovery
node bin/arwp.mjs resolve https://example.com
Explain what was found
node bin/arwp.mjs explain https://example.com
Plan for search
node bin/arwp.mjs plan https://example.com --intent=search
Observe / bootstrap ARWP profile
node bin/arwp.mjs scan https://example.com
node bin/arwp.mjs init https://example.com

The resolver treats ARWP as one publisher source, not a mandatory universal manifest. Native standards keep their own semantics.
