001

Agent tasks and protocol delivery

Preserve the useful result in text-only MCP hosts

A tool can return full structured data while its text hides the steps or limits.

v1.0.0inferredPattern reviewed 18 Oct 2026

What to do

  • For one real read-only tool, compare structuredContent with the serialized text representation.
  • Keep necessary instructions, units and limitations available in both, or supply an explicit supported resource-read path.

Check the change

  • Run the same task in a text-only consumer and a structured consumer; record unavailable host paths.

What result to look for

Record complete/partial task results by host, protocol version and representation.

Why it may help: Reliable delivery of the complete result may help an intended host finish the task; protocol success alone does not establish demand.

Watch out for: Assuming a successful tools/call proves the receiving host saw the full answer.

002

Agent tasks and protocol delivery

Keep MCP listing completeness explicit

The first page of tools or resources is not necessarily the full inventory.

v1.0.0inferredPattern reviewed 18 Oct 2026

What to do

  • Follow opaque nextCursor values within an explicit request budget; detect repeated cursors.
  • At the budget boundary preserve partial inventory and do not declare unseen capabilities absent.

Check the change

  • Test multiple pages, a cursor loop and a failure after page one; only a terminal cursor completes the listing.

What result to look for

Report pages fetched, items returned and terminal-cursor state.

Why it may help: Reliable delivery of the complete result may help an intended host finish the task; protocol success alone does not establish demand.

Watch out for: Guessing cursor values or claiming full coverage after a bounded first page.

003

Agent tasks and protocol delivery

Distinguish no match from a failed MCP task

A transport error and an empty domain result require different next steps.

v1.0.0inferredPattern reviewed 18 Oct 2026

What to do

  • Document the implemented no-match representation and the tool execution error path.
  • Test one valid result, one valid no-match input and one controlled execution failure without side effects.

Check the change

  • The consumer can distinguish domain absence, protocol failure and isError execution results without inventing content.

What result to look for

Count each result class in the fixed task set, retaining failures.

Why it may help: Reliable delivery of the complete result may help an intended host finish the task; protocol success alone does not establish demand.

Watch out for: Returning a fabricated answer to turn a failed lookup into a successful demo.

Agent tasks and protocol delivery

Test the resource read path after a tool returns a link

A discoverable resource URI may still be unusable in the intended client.

v1.0.0inferredPattern reviewed 18 Oct 2026

What to do

  • From an actual tool result, read the linked resource with the supported client and verify content type and identity.
  • Retain unsupported-host and authorization outcomes. Do not assume every resource link appears in resources/list.

Check the change

  • The saved task receipt includes the URI, read response and usable content; declaration alone stays untested.

What result to look for

Measure task completion after the read, separately from successful tool invocation.

Why it may help: Reliable delivery of the complete result may help an intended host finish the task; protocol success alone does not establish demand.

Watch out for: Counting declared resource URLs as completed user tasks.

005

Agent tasks and protocol delivery

Keep tool hints separate from action permission

An advertised read-only hint cannot authorize a write or make returned content trusted.

v1.0.0inferredPattern reviewed 18 Oct 2026

What to do

  • Treat tool metadata as hints and inspect the actual operation and data flow.
  • Use a controlled negative task to verify the host refuses an unauthorized side effect; never test destructive operations on production.

Check the change

  • A misleading annotation fixture cannot bypass the existing approval boundary.

What result to look for

Record allowed read completion and denied unauthorized actions separately.

Why it may help: Reliable delivery of the complete result may help an intended host finish the task; protocol success alone does not establish demand.

Watch out for: Treating discoverability metadata as delegated authority.

006

Agent tasks and protocol delivery

Compare an agent interface against the existing useful path

A new protocol may duplicate a simpler interface without improving the task.

v1.0.0experimentalPattern reviewed 18 Oct 2026

What to do

  • Freeze one existing user task and its correct output before comparing browser, resource and tool paths.
  • Keep client/version, task result, missing qualifiers and recovery effort; use repeated observations rather than a single polished demo.

Check the change

  • A new interface is retained only for a stated task advantage; unsupported clients and failed attempts remain in the record.

What result to look for

Compare correct useful outputs and recovery steps; external demand stays unmeasured.

Why it may help: Reliable delivery of the complete result may help an intended host finish the task; protocol success alone does not establish demand.

Watch out for: Adding MCP or WebMCP solely as an AI-search signal.
