Static metadata vs runtime evidence

Reviewed 2026-09-05CC BY 4.0
Static metadata can establish that a publisher advertises an interface. Runtime evidence can establish that a protocol endpoint or browser capability responds as observed. Neither alone proves authorization, trustworthiness, user intent, or successful task completion.
Static metadataRuntime evidence

Why the distinction matters

An A2A Agent Card can accurately describe capabilities and supported interfaces, while the callable endpoint may still require authentication or be temporarily unavailable. An MCP server can be advertised statically while authorization/runtime behavior differs. WebMCP may exist only inside a browser page runtime and therefore be invisible to a plain HTTP crawler.

ARWP therefore models static discovery as evidence, not as automatic runtime conformance. Runtime checks are separate operations with their own scope and failure states.

Current examples

MCP's 2026-07-28 specification generation emphasizes a stateless core and hardened authorization. A2A 1.0 uses Agent Cards for discovery and can declare security requirements. WebMCP exposes page functions as browser-visible tools and is inherently runtime-oriented.

Boundary

Runtime verification is not permission to execute side-effectful tools. Metadata and runtime evidence are evidence classes, not authorization.
