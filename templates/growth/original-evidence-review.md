# Original evidence: one useful artifact or observed result

Use this worksheet to *support one existing canonical page*, not to open a second experiment ledger or publish an "AI proof" story. The authoritative experiment, Change Receipt and deployed revision stay in their existing repositories. Store owner-only results privately.

## Choose the claim contract first

- **Useful artifact:** an original worked example, exercise, worksheet, diagram or functioning tool. Verify its content and actual task behavior. A useful artifact does not require a Search experiment or establish product efficacy.
- **Observed outcome:** a claim that a released change affected users, indexing, Search/AI visibility or business results. Link the existing experiment, population, production revision and actual observations; missing outcome evidence stays **unknown**.

An invented demonstration can be useful when explicitly labelled. It is not a measured result, independent research or evidence that the product works for real users. Never fabricate an experiment to satisfy this worksheet.

## 1. What the reader needs to decide

- Reader's practical problem: [one sentence in everyday language]
- Existing canonical page/job: [published URL, exact public page identity]
- One useful action they could try after reading: [one action]
- Why a reader would use this instead of a generic summary: [real distinguishing evidence, or mark **not established**]

### Inspect the existing task before adding another asset

1. Resolve the existing canonical owner and inspect its current page, linked tools and downloads. Record **already present**, **observed gap** or **not checked**; a recommendation must not recreate a working asset.
2. Ask what the visitor can actually do if an AI answer has already explained the definition. Name a useful output, decision, source artifact or verification path, not a tactic for forcing a click. If nothing distinctive is established, review value before adding prose, schema or URLs.
3. Rehearse one bounded task with deliberately synthetic, non-sensitive input. Record the starting URL, permitted steps, expected and observed output, software/source version if known, date and failure/abstention behavior. Stop before account, payment, permission or external-send boundaries not authorized by the owner.
4. Distinguish raw/build HTML, browser-rendered behavior and human benefit. Streamed content outside an initial main element needs rendered evidence; a raw parser miss is not proof that the page is empty.
5. If imagery helps, use an original explanatory visual tied to the task and visible facts. Label illustrations honestly; an AI-generated illustration is not experimental data or first-hand measurement.
6. Apply ordinary technical eligibility, visible-content/metadata parity and native interaction checks. Do not add an AI protocol, fixed chunk size, FAQ quota or schema bundle without a real consumer or applicable feature.

**Task receipt:** [existing URL] · [artifact/input class] · [actual observedAt] · [expected output] · [actual result or not checked] · [negative/abstention case] · [verification kind]. Agent review is not human verification or learning efficacy.

## 2. Real claim and provenance

| Field | Required observation |
| --- | --- |
| Question | The precise, falsifiable question, not "does AI like this site?" |
| Site/owner permission | Verified published site and right to use the underlying material |
| Frozen experiment | For an outcome claim, link the **existing** Controlled Cohort / Growth Experiment ID; do not refreeze it. For a standalone useful artifact use **not an outcome claim**, not a fabricated experiment |
| Intervention | One bounded edit/change, with implementation SHA and intended page set |
| Deployment | Independently verified live revision and date, or **not verified** |
| Source | Stable URL, owner capture or publication, with observation date and source class |
| Method | What was done and why the comparator is relevant |
| Baseline | Real observed data before the change, with population/period |
| Control | Comparable unchanged pages or documented reason no comparator exists |
| Outcome | Provider-native measured values **only where available**, otherwise **unknown** |
| Negative result | What stayed flat, worsened, contradicted the claim or could not be verified |
| Alternative cause | Releases, migrations, demand change, coverage gaps or sampling biases |
| Decision | Refer to a separate **reviewed** keep/revise/continue/revert/retire decision, if it exists |

## 3. Publishable text — not a manufactured case study

**The problem.** [Describe what a person actually struggled to do.]

**What we tried.** [Explain one real change to the existing page and why it was worth testing.]

**What we could verify.** [Separate source/build, verified live publication, indexed state, Search/AI exposure, referral, useful action.]

**What remains unclear.** [Missing data, tiny samples, anonymized queries, uncontrolled changes.]

**What happened next.** [Real reviewed decision or "we do not have a decision yet".]

When available, link an authorized reproducible public method and an original asset that genuinely helps the reader decide. Without underlying permission, summarize methodology at the appropriate disclosure level; never expose private Search Console query/page exports, credentials, workplace text or raw user observations.

## 4. Four-role release review

- **Reader:** Does the first paragraph make the choice and practical usefulness clear?
- **Practitioner:** Could another editor repeat the bounded method with their *own* evidence?
- **Skeptic:** Are denominator, chronology, confounders, negative outcomes and provenance explicit? Do not call temporal association causal.
- **Editor/rights:** Do visible prose, titles, snippets, image description and structured data make the *same true claims*, with permission and human review?

## 5. Current Search surfaces: apply selectively

The [Google Search announcement of October 15, 2026](https://blog.google/products-and-platforms/products/search/updates-ai-mode-overviews-explore-web/) describes more prominent inline links, an official-task-link display test and related links with thumbnails. These are platform features, not a new publisher schema contract or proof that a reviewed page will be selected. Test task clarity and useful imagery only when appropriate; do not manufacture news or add publication dates for carousel eligibility.

[Bing Topics Portfolio Beta, October 13, 2026](https://blogs.bing.com/webmaster/2026/10/introducing-topics-portfolio-beta-in-ai-performance/) can inform a topic-to-existing-page review **if the owner's report is available**. Preserve approximate topic measures and citation ranges as supplied, review competitor-branded and off-topic queries, and keep missing topics unknown. Never turn range midpoints into exact counts, derive GSC demand from Bing citations or create one page per opportunity query. A beta topic label is not a ranking instruction.

## 6. Stop conditions

Do not publish a success story when the publication revision is not independently confirmed, the outcome period predates the intervention, owner data is missing or preliminary, control pages have changed unrecorded, or the example needs fabricated users/metrics. Keep a truthful methodology page or a neutral outcome instead.
