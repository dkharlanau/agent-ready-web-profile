# Technical evidence review worksheet

Version: 1.0.0. Project workflow, not a ranking requirement.

Record the site, commit, corpus and pattern versions, reviewer, date and exact sample before running checks. Keep unknown values unknown. Exclude private URLs and credentials from public reports.

| Interview question | Evidence to collect | Common false conclusion |
| --- | --- | --- |
| Can the intended client retrieve the answer? | Initial HTML, rendered HTML, HTTP response and verified crawler access as separate observations | A successful local fetch proves Google indexing |
| Is every intended collection record reachable? | Frozen expected ID set, bounded traversal, missing IDs, repeats and loops | Every repeated card is an SEO defect |
| Does the graph describe actual entities? | Visible facts, stable IDs, meaningful primary-subject and citation relations | Resolving an ID proves its claim |
| Can another person reproduce the data result? | Exact release, dictionary, query, output, exclusions and reuse terms | Valid JSON proves data quality |
| Did the change improve acquisition? | Fixed cohort, observation window, owner-side search and business evidence | More markup or a green validator proves growth |

For each correction record: previous instruction, source section, supported claim, inferred extension, revised instruction, verification result and rollback. Start with one representative page per relevant template and expand only when failures or unresolved variation justify it. There is no universal sample size.
